Your agent drafts. You decide. Steerpost posts once.

  1. Your agent drafts

    Create an MCP connection, tick the permissions you are comfortable with and paste the config into your agent. By default it can only read and draft. Scheduling, publishing and deleting stay off until you allow them.

  2. You approve the risky part

    Publishing now, deleting, disconnecting and scheduling within minutes wait on the Approvals page. You read what the agent wants to post, then approve or deny. An approval works once.

  3. Steerpost posts it once

    A worker publishes at the scheduled time and retries failures that are safe to retry. If it cannot tell whether a post went out, it stops and asks you.

Agents work within limits you set

Agents such as Claude Desktop connect through the Model Context Protocol and use the same REST API as the app, with the caller's own key. The MCP server holds no state and no social credentials, so it can never bypass authorization.

Permission model

  • Scoped keys. Tools a key has no scope for are not even listed, and the REST API checks the scope again on every call.
  • Dangerous actions are opt-in. publish_post, delete_post and disconnect_account are off by default, and every call needs your approval in Steerpost before it runs.
  • Revocable and expiring. Keys are stored as SHA-256 hashes and shown once. Revoking a connection invalidates its key immediately.
  • Audited. Every agent action lands in the audit log as api_key:<name>. Keys can never create keys or change account security.

Connect an agent

Create a connection under Developer, then paste the generated config. For example, for an HTTP client:

{
  "mcpServers": {
    "steerpost": {
      "type": "http",
      "url": "http://localhost:3333/mcp",
      "headers": { "Authorization": "Bearer sk_live_..." }
    }
  }
}

Then ask: "Write a post about my new Flutter project and schedule it for tomorrow 12:00 on LinkedIn and Telegram."

Built so a post goes out once

A visible miss beats a duplicate. These are the rules the publisher follows.

At most one publish per target

Each target carries an idempotency key. If a worker crashes between the network call and the database write, the target becomes needs_review instead of being posted again.

Retries only where they are safe

Network errors, 5xx responses and rate limits back off exponentially, up to {{retryCount}} retries. Permanent and authorization errors fail visibly, with the reason attached to the attempt.

Secrets stay secret

OAuth tokens are encrypted with AES-256-GCM and never logged. Browser sessions are opaque server-side sessions with CSRF protection. Every query is scoped to its owner.

A scheduler you can reason about

The database is the source of truth and Redis only carries jobs. A reconciler re-enqueues anything that is due but missing, so a Redis flush does not lose scheduled posts.

Run it yourself

Steerpost is self-hosted. One command starts Postgres, Redis, MinIO, the API, the worker, the MCP server and the web app. With the mock network enabled you can try the whole flow without any credentials.

Local setup, environment variables, OAuth setup and the full API are in the documentation.

make up        # generates .env, then docker compose up
open http://localhost:3000

See it work before you read about it.
